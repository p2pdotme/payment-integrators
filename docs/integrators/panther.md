# PantherBuyUsdcIntegrator

Integrator for **Panther Wallet** (custodial wallet, mypanther.io). Panther's customers buy **USDC only**, paying in local currency (PIX, UPI, Alias/CBU, Pago Móvil, QRIS…) to a P2P merchant. The USDC goes to **Panther's treasury on Base**, and Panther credits the customer's internal balance off-chain when the order completes.

The contract has a single role that can start a flow: Panther's server (`operator`). End users never sign on Base.

## Flow

1. The customer picks a currency and a USDC amount in the Panther app. Panther's server reads `getPriceConfig`, chooses an eligible circle (the same weighting and `getAssignableMerchantsFromCircle` check the SDK uses), and calls:

   `operatorPlaceOrder(cuenta, amount, currency, circleId, pubKey, preferredPaymentChannelConfigId, fiatAmountLimit)`
   - `cuenta` is `keccak256("panther.cuenta." + internalAccountId)`. It is an opaque bytes32 with no personal data.
   - The keyless user is `usuarioDe(cuenta)`, an address derived from that hash. Its canonical `UserProxy` (CREATE2, unmodified) is `order.user`.
   - `recipientAddr` is always the immutable `treasury`.
   - `pubKey` is a fresh secp256k1 key per order, generated by the server. The merchant encrypts its payment details to it (ECIES, the SDK format), and the server decrypts them and shows them to the customer.

2. A merchant accepts the order. The customer pays off-chain and taps "I paid". The server calls `operatorMarkPaid(orderId)`, which forwards `paidBuyOrder` from the proxy.
3. The merchant releases. The Diamond sends USDC to `treasury` and calls `onOrderComplete`. The contract emits `PantherOrderCompleted`. The server checks that `recipient == treasury` and the amount, and credits the customer exactly once per `orderId`.
4. Abandoned orders: the server calls `operatorCancelOrder(orderId)` 15 min after placement with no merchant, or after the merchant's payment window plus a grace period. Orders also expire through the Diamond's TTL.

## Limits

| Limit                                       | Initial value proposed | Hard ceiling (compiled in) |
| ------------------------------------------- | ---------------------- | -------------------------- |
| `perTxCap`                                  | 50 USDC                | 500 USDC                   |
| `dailyTxCountLimit` (per `cuenta`, UTC day) | 10                     | 50                         |
| `dailyVolumeCap` (per `cuenta`)             | off (0)                | 5,000 USDC                 |

On top of these, Panther enforces its own KYC level, min/max and per-day count server-side, plus one open order per customer at a time.

## Roles and safety

- `owner` = the deployer. It is immutable and cannot be transferred, and it is meant to be a cold wallet. It can rotate `operator`, tune caps within the ceilings, and `pause`/`unpause`.
- `pause` blocks new orders and operator cancels. It never blocks `operatorMarkPaid`, because the customer's fiat already left their bank, and it never blocks Diamond callbacks.
- The contract does not hold USDC in the normal flow. `flushToTreasury()` (callable by anyone, only destination `treasury`) exists only for a mis-registration (`usdcThroughIntegrator = true`, flagged by `SettlementRoutingAnomaly`) or accidental transfers.
- A cancelled order that later completes through dispute emits `CancelledOrderCompleted` and is still credited.

## Registration

- `usdcThroughIntegrator`: **false**.
- `proxyImpl`: the value `proxyImpl()` returns after deploy.
- Cancel callback: requested (`setIntegratorCancelCallback(integrator, true)`), so expired orders release the daily count.
- Expected currencies: INR, IDR, BRL, ARS, BOB, VEN, NGN, COP, PEN, ECU, with their circles as listed by the subgraph. We will start with the live ones: BRL, ARS and INR.

## Tests

`test/PantherBuyUsdcIntegrator.test.ts` (44 cases on `MockDiamond`/`MockUSDC`) covers:

- placement, paid, complete and cancel;
- the per-tx, count and volume caps and the UTC day roll-over;
- `pause` semantics;
- operator and owner gating;
- treasury-only delivery;
- the routing anomaly and flush;
- cancelled-then-completed orders;
- proxy address determinism.
